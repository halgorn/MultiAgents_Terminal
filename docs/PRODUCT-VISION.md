# Product Vision — aion as RAG Confidence Layer

This document describes the end state of aion as the **RAG Confidence Layer** for any LLM agent (Cursor, Claude Code, Codex, OpenCode). It is the source of truth for product decisions.

## The problem

When a developer asks an LLM agent a question about a codebase, today the agent has two options:

1. **Read raw files** — burns 10k+ tokens per question, repeats work, gets out of date.
2. **Use a vector DB** — fast but the agent has no way to know if the index is fresh. The agent may cite code that was deleted hours ago.

Neither option gives the agent **data confidence** — the ability to know, on every response, *how much to trust the index*.

## The vision

aion sits between the agent and the codebase. It maintains a unified **Project Intelligence Layer (PIL)** that the agent can read through MCP. Every response carries metadata about index freshness, so the agent can decide whether to trust the result or re-read the source.

```
┌──────────────────────────────────────────────────────────────┐
│  Agent (Cursor, Claude Code, Codex, OpenCode)                │
│                                                              │
│  Recebe de cada response:                                    │
│  {                                                           │
│    content: "auth.ts has 3 functions...",                    │
│    _meta: {                                                  │
│      pilVersion: 1,                                          │
│      indexedAt: "2026-06-18T12:34:56Z",                      │
│      filesChangedSince: 0,                                   │
│      confidence: "high",                                     │
│      syncRecommended: false,                                 │
│      estTokens: 412,                                        │
│      traceId: "a1b2c3"                                       │
│    }                                                         │
│  }                                                           │
│                                                              │
│  Decisão do agente:                                          │
│  - high    → cita direto (responde em ~2k tokens)            │
│  - medium  → cita com nota "pode estar desatualizado"        │
│  - stale   → chama tool "read_file_lines" pra confirmar      │
└──────────────────────────────────────────────────────────────┘
```

## The three pillars

### 1. PIL — the data layer

A single, versioned, self-describing artifact persisted at `.ai-runtime/project.json` (plus `.ai-runtime/project.vectors.bin` for Float32 embeddings). One source of truth for:

- Files, symbols, imports, AST chunks
- Dependency graph (nodes, cycles, hotspots)
- Test coverage mapping
- Embedding metadata (model, dimensions, count)

See [ADR 002](adr/002-project-intelligence-layer.md).

### 2. MCP — the distribution layer

The MCP server is **self-sufficient**. On connect it:

- Checks PIL freshness; syncs if stale or missing
- Starts a file watcher in the background
- Exposes tools, resources, and prompts
- Returns metadata on every response

Clients (Cursor, Claude Desktop, Codex, OpenCode) configure aion once via `aion mcp install --client <name>`.

### 3. Freshness — the confidence layer

Every response carries a `confidence` field:

| Confidence | Trigger | Agent behavior |
|---|---|---|
| `high` | 0 files changed, < 5 min | Cite directly |
| `medium` | 1-3 files changed, < 30 min | Cite with caveat |
| `stale` | > 3 files changed or > 30 min | Re-read source before citing |

The watcher increments `filesChangedSince` automatically. The auto-sync fires when `stale` is detected on a tool call.

## The data model: RAG multi-doc

In addition to the PIL, aion can generate specialized `.md` documents, each with its own access policy. The `PROJECT.md` dashboard is the default; sub-docs are generated on demand.

```
.ai-runtime/
├── project.json              ← PIL (source of truth, generated by `aion sync`)
├── project.vectors.bin
├── PROJECT.md                ← dashboard (1.5k tokens, auto-include)
└── docs/
    ├── architecture.md       ← modules, deps, cycles
    ├── security.md           ← OWASP findings, secrets, vulnerable deps
    ├── performance.md        ← hot paths, complexity
    ├── test-coverage.md      ← gaps, untested modules
    ├── dependencies.md       ← outdated, advisories
    ├── modules/
    │   ├── auth.md           ← one per module
    │   └── ...
    └── recent-changes.md     ← last N commits
```

Each sub-doc has frontmatter declaring its access policy:

```markdown
---
generated_at: 2026-06-18T12:34:56Z
schema_version: 1
freshness: realtime      # realtime | sync | lazy
audience: user           # user | assistant | both
priority: 0.3            # 0.0 (on-demand) to 1.0 (auto-include)
token_cost: 1200
---
```

MCP `Resource.annotations` carry the same metadata to the agent, so the IDE knows what to auto-attach to context.

## The flow

### Phase 0 — Setup (one-time per project)

```bash
aion mcp install --client cursor    # writes .cursor/mcp.json
aion sync                            # generates PIL
aion wiki --all                      # generates PROJECT.md + sub-docs
```

### Phase 1 — IDE opens project

```
Cursor startup
  ↓ reads .cursor/mcp.json
  ↓ spawns `aion mcp serve` (stdio)
aion MCP server
  ↓ checks PIL freshness → fresh, loads (50ms)
  ↓ starts fs.watch on src/
  ↓ sends ListTools + ListResources + ListPrompts
Cursor agent
  ↓ receives priority ≥ 0.7 resources in context
```

### Phase 2 — User asks a question

```
User: "como funciona auth?"
Cursor agent
  ↓ already has aion://docs/architecture in context
  ↓ tool_call: search_memory(query="auth", topK=5)
aion server
  ↓ checks: confidence = high (0 files changed)
  ↓ searches vectors.bin (30ms)
  ↓ returns top-5 chunks + _meta
Cursor agent
  ↓ cites with confidence "high" — 2k tokens total
```

### Phase 3 — User edits a file

```
Cursor saves src/auth/middleware.ts
  ↓ fs.watch fires
aion server
  ↓ filesChangedSince++
  ↓ re-sync incremental (200ms)
  ↓ emits notifications/resources/updated
Cursor
  ↓ knows resource changed, may re-read on next question
```

## The economics

| Scenario | Tokens per question |
|---|---|
| Without aion (5 Read tools) | ~10,000 |
| With aion v1 (single tool call) | ~3,000 |
| With aion v2 (resource + tool) | ~2,000 |
| With aion v2 + multi-doc (specific sub-doc) | ~800 |

The user pays ~80% less per question, and the agent cites code with a `confidence` score instead of hoping it's right.

## Why this is the moat

| Component | Easy to copy? |
|---|---|
| Vector search | Yes (everyone has it) |
| Embeddings | Yes (Xenova, OpenAI, Voyage) |
| MCP server | Medium (MCP is open, but the integration takes work) |
| Unified PIL | Medium (the schema design is non-trivial) |
| **Freshness signaling** | **Hard (the value is in the protocol, not the storage)** |
| **Multi-doc with access policy** | **Hard (MCP annotations + freshness interplay)** |

The first 3 layers are commoditized. The 4th and 5th are what aion owns.

## Open questions

- Should `aion://docs/security` ever be auto-included? (Default: no — security findings are sensitive.)
- Should the `PROJECT.md` be committed to git by default, or always gitignored? (Default: gitignored. Future: opt-in via `.aionrc.json`.)
- Should we ship an HTTP transport alongside stdio? (Default: no for v1.0 — most clients are local.)
